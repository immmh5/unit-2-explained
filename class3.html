Class 3: ميثاق المشروع وخط أساس العملية

السؤال الجوهري للدرس كله: اختيار نموذج العملية لا يكفي — الفريق الحقيقي لازم يتفق على كيف ستشتغل هذه العملية فعلياً.
"اختيار الـ process مجرد بداية. الفريق يحتاج اتفاق يحدد: مين يقرر، مين يوافق، كيف نعرف إن الشغل جاهز، ووش نسوي لو تغيرت المتطلبات."

⭐ الملخص السريع

  1. ① اختيار دورة الحياة لا يكفي — الفريق يجب أن يتفق على كيف ستعمل تلك العملية فعلياً.
  2. ② الـ Project Charter هو هذا الاتفاق — خمس أجزاء: Purpose, People, Flow, Gates, Adapt.
  3. ③ الـ Purpose يضع الحدود (داخل/خارج النطاق)؛ الـ Flow + Gates تجعل العمل قابلاً للتحكم؛ الـ Adapt + Trace تجعله قابلاً للمراجعة.
  4. ④ الـ Process Baseline يحوّل الاتفاق إلى خطوات ملموسة: Plan → Design → Build → Test → Release — لكل خطوة مسؤول ومخرج وفحص وتغذية راجعة.
  5. ⑤ كل تغيير يُراجَع أولاً، ثم يُوافَق عليه من صاحب الـ Decision Right، ثم يُسجَّل في الـ Trace.
  6. ⑥ لا شيء ينتقل إلى Release حتى يكون gate evidence كاملاً.

🧸 الشرح كأني طفل سنة أولى

تخيلك وأصحابك فتحتوا كشك عصير ليمون 🍋. قبل ما تبدأوا تبيعوا، لازم تتفقوا على أشياء:

  • ① مين يسوي وش (People): مين يعصر، مين يبيع، مين يقبض الفلوس، ومين يتقرر لو صار خلاف.
  • ② وش في القائمة (Purpose / Scope): عصير ليمون بس — الكوكيز خارج 🚫! ما نبيعها هاليومين.
  • ③ كيف نسويها (Flow): الخطوات — قطّف → اعصر → حلّي → قدّم.
  • ④ فحص الذوق (Quality Gate): قبل أي كوب يطلع للزبون، واحد منكم يذوقه. لو حامض زيادة → يرجع يتعادله.
  • ⑤ لو طلبوا نكهة جديدة (Adapt): ما نطبخها فوراً! نجلس نفكر: هل نضيفها؟ كم تكلف؟ مين يقرر؟ ونسجل إننا غيرنا القائمة.

الخلاصة: الاتفاق الكامل هذا (مين، وش، كيف، فحص، تغيير) هو الـ Project Charter 📜. خطوات الوصفة نفسها هي الـ Process Baseline 🪜. وفحص الذوق قبل التقديم هو الـ Quality Gate ✅.

🔄 قبل ما نبدأ — مراجعة سريعة + السؤال المحفّز

مراجعة الدرس السابق:

  • مشروع متطلباته ثابتة وإصدار واحد مخطط له → Predictive ✔️
  • فريق يحسّن نفس الميزة بعد كل اختبار مستخدم → Iterative ✔️
  • تغييرات كثيرة + كل إصدار يحتاج موافقة رسمية → Hybrid ✔️

⚠️ السؤال المحفّز (Hook):

"فريق بدأ يبرمج فوراً. لا أحد يعرف مين يقدر يوافق على التغييرات، وش الدليل المطلوب، ولا متى مسموح الإصدار."

قبل ما الفريق يبدأ، على وش لازم يتفقوا عشان يبقى الشغل متحكم فيه ومسؤولاً؟

الجواب المتوقّع: اتفاق واضح قبل البداية — مين يحدد النطاق، مين عنده صلاحية الموافقة، كيف نعرف إن الشغل جاهز للمرحلة التالية، ووش نسوي لو تغيرت المتطلبات.

نحتاج PROJECT CHARTER يحدد اتفاق الفريق الأساسي + PROCESS BASELINE يحدد كيف يجري الشغل وأي ضوابط مطلوبة 🎯
LEARNING OBJECTIVES

🎯 أهداف الدرس

1 · Create a Project Charter

تعرّف النطاق، أصحاب المصلحة، أدوار الفريق، القرارات، التواصل، ومخرجات العمل.

2 · Defend a Process Decision

اشرح ليش فريقك اختار هذه العملية، وحسّنها لما يتغير المشروع.

3 · Create a Process Baseline

بيّن خطوات العمل، التغذية الراجعة، التغييرات، الأدلة، وفحوصات الجودة.

DEFINITION

📜 ما هو الـ Project Charter؟

"Project Charter is the team's agreed guide for how the project will run."
الميثاق هو الدليل المتفق عليه بين الفريق لكيفية إدارة المشروع — يحدد الهدف، الناس، سير العمل، بوابات الجودة، ومتى تُراجَع العملية أو تُغيَّر.
⚠️ فخ شائع: الميثاق ليس وصفاً قصيراً للتطبيق ("نحن نصنع تطبيق طلبات طعام") — بل هو اتفاق تشغيل الفريق (operating agreement).

أجزاء الميثاق الخمسة (احفظها بالإنجليزي):

🎯
① PURPOSE

حدد المشكلة، المستخدمين، القيمة، مقاييس النجاح، الاستثناءات، والحدود الأخلاقية/السلامة.

👥
② PEOPLE

حدد الأدوار، ملكية المخرجات (artefact ownership)، صلاحيات القرار، واجبات المراجعة، تواصل الفريق، وكيف تطلب المساعدة.

🔀
③ FLOW

ارسم الاكتشاف، التصميم، البناء، التحقق، الإصدار مع حلقات التغذية الراجعة وحدود العمل المرئية.

🚦
④ GATES

حدد الدليل المطلوب لكل من: الخطوط الأساسية، المراجعات، الاختبارات، الموافقة على التغيير، وقرار الإصدار أو عدمه.

🧭
⑤ ADAPT

اضبط محفّزات المراجعة (review triggers) عشان يغيّر الفريق العملية بوعي، مع الحفاظ على التتبع والمساءلة.

OPTIONAL HANDS-ON

🍽️ تحدي تطبيق طلبات الطعام (Food Ordering App)

الزبون يختار وجبة وشراب ثم يدفع أونلاين. أكواد الخصم خارجة (OUT) للحين. مدير المطعم يوافق على التغييرات الكبيرة والإصدار النهائي.

▶ ① CHARTER — أسئلة الميثاق

الأسئلة: وش هدف التطبيق؟ سمِّ شيء واحد خارج النطاق. مين يبني التطبيق؟ مين يختبره؟

✅ الإجابات:

الهدف: تطبيق يخلّي الزبون يطلب وجبة وشراب ويدفع أونلاين بسهولة. خارج النطاق: أكواد الخصم 🚫. يبنيه: فريق التطوير. يختبره: فريق الاختبار (Tester).

▶ ② MAP — رتّب المراحل

السؤال: رتّب: Verify, Discover, Release, Build, Design

✅ الجواب: Discover → Design → Build → Verify → Release

لو وجد الـ Verify خطأ برمجياً، وين يروح الشغل؟ → يرجع لـ Build عشان يُصلح، ثم يُعاد التحقق 🔁

▶ ③ CHECK BEFORE RELEASE — افحص قبل الإصدار

السؤال: التطبيق جاهز، لكن الطلب لم يُختبر. تصدر أو تمسك؟

✅ الجواب: Hold (امسك) ✋

وش لازم يُختبر؟ عملية الطلب كاملة (اختيار، دفع، تأكيد). وش الدليل اللي يُحفَظ؟ نتائج الاختبارات (test results) كأدلة (Evidence) 📦

▶ ④ THE PROJECT CHANGES — المشروع تغيّر

السؤال: المطعم يطلب إضافة "إلغاء الطلب". نبنيها الحين؟

✅ الجواب: لا — راجِع أولاً 🛑

وش يراجع الفريق أولاً؟ تأثيرها على النطاق (scope) والجدول (schedule). لو تمت الموافقة، وش يُحدَّث ويُسجَّل؟ الميثاق + خط الأساس + سجل التتبع (trace record) 📝

FINAL CHECK

✅ الاختبار النهائي — سيناريوهات

▶ السيناريو 1: الفريق اكتشف أن المدرسين ما يقدرون يسجلون الحضور صح. وش يسوون؟

A) أصدره ووثّقه / B) عطّل الميزة / C) أصلح واختبر مرة ثانية / D) تقبّل المخاطرة

✅ الجواب: C — Fix and test again

العيب يُصلح ثم يُعاد اختباره قبل أي إصدار — لا تصدر شيئاً معطوباً.

▶ السيناريو 2: طالب يطلب إضافة ميزة الدرجات، مو ضمن النطاق الأصلي. وش يسوون الفريق؟

A) أضفها الحين / B) راجع تأثيرها / C) خبّرها لوقت لاحق / D) ارفضها

✅ الجواب: B — Review its impact

أي طلب خارج النطاق يُدرَس تأثيره على النطاق والجدول أولاً، ثم يُتخذ القرار.

▶ السيناريو 3: الفريق عنده Tester، بس محدداً مين يقدر يوافق على الإصدار النهائي. وش ناقص؟

A) ملكية المخرجات / B) واجب المراجعة / C) صلاحيات القرار / D) خطة التواصل

✅ الجواب: C — Decision Rights

"مين يوافق على الإصدار" = Decision Right — حق اتخاذ قرار المشروع.

▶ السيناريو 4: الفريق يبي ينتقل من Testing إلى Release. وش لازم يكون عندهم أولاً؟

A) دليل البوابة كامل / B) كل الميزات خلصت / C) الكل يوافق / D) ما فيه تغييرات مستقبلية

✅ الجواب: A — Gate evidence is complete

الانتقال بين المراحل يحتاج أدلة (Evidence) تثبت جاهزية العمل — وليس مجرد اكتمال الميزات.

🔥 حيل الاختبار (Exam Hacks)

إذا شفت: "who approves", "who has the authority" → الجواب: Decision Right
إذا شفت: "what's in and out", "excluded from the project" → الجواب: Scope
إذا شفت: "check before moving forward", "requires evidence" → الجواب: Quality Gate
إذا شفت: "making the software available to users" → الجواب: Release
إذا شفت: "a document or work product" → الجواب: Artefact
إذا شفت: "the agreed way to do the work" → الجواب: Process Baseline
إذا شفت: "the team's operating agreement", "agreed guide for how the project runs" → الجواب: Project Charter
إذا شفت: "information that helps improve the work" → الجواب: Feedback
