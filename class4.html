Class 4: من "كود يشتغل" إلى "نظام يخدم ناس"

السؤال الجوهري للدرس كله: متى يكون الكود الصحيح غير كافٍ؟ — تخيل كود يشغل الميزة تماماً... هل هذا يكفي عشان مستخدمين حقيقيين يعتمدون عليه؟ الجواب: لا، وفي هذا الدرس ستكتشف كل الأشياء الثانية اللي لازم تتأكد منها.

🧸 الشرح كأني طفل سنة أولى

تخيلك بنيت برج مكعبات 🧱. أنت فرحان لأنه ما انكسر. هل هذا يخليه "جاهز للناس"؟

  • ① الكود (Code): المكعبات نفسها — هل البرج واقف؟ ✅ واقف.
  • ② النظام (System): البرج + الأرض اللي واقف عليها + يد أخوك الصغير اللي بيدفعه + القواعد (محد يلمسه) — كل هذا جزء من "الشيء".
  • ③ القيمة (Value): هل أحد فعلاً يستفيد من البرج؟ مثلاً: هل هو مزخرفة عشان تبيعه؟

الخلاصة: المبرمج يفكر في "المكعبات" فقط. المهندس (Engineer) يفكر في كل المكعبات والأرض والناس والوقت والمخاطر — ويفكر في المستقبل: وش يصير لو أخوك الكبير حب يزود دور ثاني للبرج؟ لازم تبنيه من البداية بطريقة تتحمل!

OBJECTIVE 1

🧩 البرمجة جزء من نظام أكبر (Code → System → Value)

💻
1 · CODE

المبرمج يكتب كود عشان الميزة تشتغل. Construct (يبني).

⚙️
2 · SYSTEM

البرنامج أكبر من الكود — فيه أجزاء متصلة. Operate (يشغل).

⭐
3 · VALUE

نبدأ من حاجة المستخدم المعتمدة. Sustain (يدوم).

OBJECTIVE 1 (تابع)

⏳ الهندسة تفكر في الزمان: Change · Quality · Evidence

1 · CHANGE PLAN

خطط لتغير الاحتياجات، الأخطاء، البيئات، وانتقال الملكية. أول بناء ليس نهائياً! البناء الأول دايماً prototype.

2 · QUALITY CHECK

الجودة تشمل Reliability (الاعتمادية) + Security (الأمان) + Usability (سهولة الاستخدام) + Maintainability (قابلية الصيانة). التوقعات لازم تطابق المخاطرة.

3 · EVIDENCE SHOW

الدليل يشمل Artefacts (مخرجات) + Reviews (مراجعات) + Tests (اختبارات) + Versions (إصدارات) + Limitations (الحدود) — أشياء أي شخص ثاني يقدر يفحصها.

❌ "I think it works" ليس دليلاً — "أنا أعتقد أنه يشتغل" غير مقبول
OBJECTIVES 2 & 3

✅ جاهز أولاً، ثم حدد المشكلة (Readiness → Bounded Problem)

1 · Prerequisite Readiness (الجاهزية)

Approved case — تعرف بالضبط وش مسموح للمشروع يسويه.
Approved toolchain — تستخدم بس الأدوات المسموح بها.
Evidence rules — تعرف وش الدليل المطلوب تسجله.
Readiness gap — تسمي وش الدعم اللي ناقصك بعد.

2 · Bounded Engineering Problem (المشكلة المحدودة)

User need — مين يحتاج وش؟
Stakeholder value — وش النتيجة المفيدة اللي يفترض البرنامج يخلقها؟
Credible success signal — وش الدليل القابل للقياس اللي يبرز التقدم؟
Boundary — وش اللي داخل بوضوح وخارج بوضوح من المشكلة؟
⚠️ فخ الاختبار: Ready ≠ Confident — الجاهزية ليست الثقة! الجاهزية تعني أن الـ approved case, tools, evidence rules واضحة ومحددة. الثقة شعور، الجاهزية حقائق مكتوبة.
PROCESS MODELS

🛤️ نماذج العمليات (Process Models)

كيف نختار طريقة سير المشروع؟ كل نموذج له سؤال الجاهزية الخاص.

📐 Predictive (Waterfall)النموذج التقليدي

الفكرة: نخطط كل شيء من البداية، ثم ننفذ بالترتيب: Plan → Design → Build → Test → Release

سؤال الجاهزية: "Are requirements stable and approved?" — هل المتطلبات ثابتة ومعتمدة؟

✅ مناسب لما تكون المتطلبات واضحة 100% (مثل الأنظمة الحرجة، الطب، الطيران) | ❌ سيء لو المتطلبات تتغير

🔁 Iterativeتحسين متكرر

الفكرة: نبني نسخة، نعرضها، نتعلم، نحسن نفس الشيء مراراً. كل دورة (iteration) تحل مشكلة أعقد.

سؤال الجاهزية: "Can we improve understanding through feedback?"

✅ ينفع تشرح وتوضح الفكرة أكثر فأكثر | 🎯 يركز على reduce risk & refine understanding

🧱 Incrementalأجزاء تتراكم

الفكرة: نبني البرنامج في أجزاء صغيرة قابلة للاستخدام (slices)، كل جزء يسلم قيمة حقيقية، ونتجول الأجزاء.

سؤال الجاهزية: "Can we deliver usable parts early?"

✅ تكسب مستخدمين مبكراً | 🎯 يركز على early value, usable increments

⚡ Agileسرعة ومرونة

الفكرة: سprints قصيرة (1-4 أسابيع)، نتكيف مع التغيير، ونعيد ترتيب الأولويات كل مرة بناءً على feedback.

سؤال الجاهزية: "Can we adapt quickly to change?"

✅ التغيير شيء طبيعي ومطلوب | 🎯 working software over documentation

🔀 Hybridخلط الأفضل من الاثنين

الفكرة: نستخدم Predictive للأجزاء الثابتة الحرجة (مثل الأساسيات والأمان) و Agile للأجزاء المتغيرة (مثل الواجهات والميزات).

سؤال الجاهزية: "Which parts are stable and which must adapt?"

✅ واقعي في معظم الشركات الكبيرة

PROJECT CHARTER

📜 ميثاق المشروع (Project Charter)

وثيقة قصيرة تقول "مين يسوي وش، ليش، وكيف نعرف أننا نجحنا" — بدون ما تشرح كل التفاصيل.

🎯 Purpose / Project Goal

الهدف — ليش هذا المشروع موجود أصلاً

👥 Team Roles

الأدوار — مين مسؤول عن وش (بالاسم)

📦 Project Scope

النطاق — وش داخل ووش خارج

📈 Success Criteria

معايير النجاح — كيف نقول "نجحنا"

⏱️ Timeline / Milestones

الجدول — نقاط التسليم

🚧 Constraints & Assumptions

القيود والافتراضات — وش اللي يحدنا

Process Baseline (خط الأساس للعملية): نسخة معتمدة ومجمّدة من طريقة العمل — من اللحظة اللي تتجمد فيها، أي تعديل يحتاج Change Request رسمي (راجع Class 6).

🛠️ تطبيق عملي (Hands-on)

هذه نفس أسئلة الـ Activity في الدرس — حاول تحلها قبل ما تشوف الإجابة:

▶ السؤال 1: الميزة تشتغل. أي مهمة تعتبر Software Engineering أساساً؟

A) أضف فحص لنوع الملف واختبره
B) خطط كيفية التعامل مع المستخدمين والتحديثات والأخطاء
C) أعد هيكلة دالة الرفع وحدث التعليقات

✅ الجواب: B

لأن التخطيط للمستخدمين والتحديثات والأخطاء = تفكير عبر الزمن (Change) — وهذا جوهر الهندسة. A و C مجرد برمجة (كود فقط).

▶ السؤال 2: الفريق يعرف Python. أي خيار يبين الجاهزية (Readiness)؟

A) Approved case, allowed tools, evidence rules, readiness gap
B) Approved case, familiar tools, coding rules, first feature
C) Project goal, allowed tools, team confidence, first feature

✅ الجواب: A

الجاهزية = الـ 4 عناصر الرسمية. "Familiar tools" و "Team confidence" فخ! — تذكرك: Ready ≠ Confident.

▶ السؤال 3: أي مشكلة "محدودة" (bounded) بشكل صحيح؟

A) رفع أسهل؛ النجاح = أغلب الطلاب يفضله
B) (الخيار الأفضل: نطاق محدد + إشارة نجاح قابلة للقياس)

✅ الجواب: B — المشكلة المحدودة لازم فيها User need + Stakeholder value + Credible success signal (رقم قابل للقياس)

"أغلب الطلاب يفضله" مشكلة: تفضيل ليس قياساً! لازم شيء مثل "نسبة الرفع الناجح ≥ 95% خلال 60 ثانية".
