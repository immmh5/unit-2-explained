Class 1: العقلية الهندسية والجاهزية

السؤال الجوهري للدرس كله: متى يكون الكود الذي يشتغل غير كافٍ؟ 🤔 — الكود يشغّل الميزة ويعطيك النتيجة المتوقعة... هل هذا دليل كافٍ على أن البرنامج جاهز للاستخدام الحقيقي؟ الجواب: لا! في هذا الدرس ستكتشف كل الأشياء الثانية اللي على المهندس يتأكد منها.

⭐ الملخص السريع (الترتيب المنطقي للدرس)

  1. 1

    البرمجة تخلي الكود يشتغل بس — أما Software Engineering فتهتم بـ النظام كامل (Code + Data + People + ...) وقيمته مع الزمن.

  2. 2

    الهندسة مع الزمن تعني: تخطط لـ CHANGE (التغيير)، وتفحص QUALITY (الجودة)، وتُظهر EVIDENCE (الدليل).

  3. 3

    "I think it works" ليس دليلاً — Evidence لازم يكون شيء يقدر شخص ثاني يفحصه.

  4. 4

    قبل ما تحدد المشكلة، افحص Prerequisite Readiness: Approved case + Approved toolchain + Evidence rules + Readiness gap.

  5. 5

    بعدها عرّف Bounded Engineering Problem: User need + Stakeholder value + Credible success signal + Boundary.

  6. 6

    Ready ≠ Confident — الجاهزية ليست الثقة! الجاهزية حقائق مكتوبة وواضحة.

🧸 الشرح كأني طفل سنة أولى

تخيلك بنيت برج مكعبات 🧱. أنت فرحان لأنه واقف وما انكسر. هل هذا يخليه "جاهز للناس"؟

  • ① الكود (Code): المكعبات نفسها — هل البرج واقف؟ ✅ واقف. هذا اللي يفكر فيه المبرمج.
  • ② النظام (System): البرج + الأرض اللي واقف عليها + يد أخوك الصغير اللي بيدهدها + القواعد (محد يلمسه) — كل هذا جزء من "الشيء".
  • ③ القيمة (Value): هل أحد فعلاً يستمتع بالبرج أو يستفيد منه؟ هل فرحت أخوك الصغير لما شافه؟

الخلاصة: المبرمج يفكر في "المكعبات" فقط. المهندس (Engineer) يفكر في المكعبات + الأرض + الناس + القواعد + المستقبل — وش يصير لو حاب يزودون دور ثاني؟ لازم تبنيه من البداية بطريقة تتحمل التغيير!

🎯 أهداف الدرس (Learning Objectives)

1) أميّز بين مهام البرمجة ومسؤوليات Software Engineering عبر أربعة محاور: الزمن (Time)، الناس (People)، التغيير (Change)، والمخاطرة (Risk).
2) أُقيّم الجاهزية المسبقة (Prerequisite Readiness) باستخدام قواعد: الـ approved case، الـ toolchain، وقواعد الدليل (evidence rules).
3) أُعرّف مشكلة هندسية واحدة محدودة (Bounded Engineering Problem): حاجة المستخدم، Stakeholder value، وإشارة نجاح موثوقة (credible success signal).
OBJECTIVE 1

🧩 من الكود إلى القيمة (Code → System → Value)

💻
1 · CODE

البرمجة تنشئ كود أو تعدله عشان الميزة تشتغل. Construct (بناء).

⚙️
2 · SYSTEM

البرنامج أكبر من الكود — هو نظام من أجزاء متصلة.

⭐
3 · VALUE

الهدف هو قيمة مستدامة للمستفيدين (Sustained stakeholder value).

🗄️

🔌

الدليل الذي يربطها كلها

👁️ النظرة الهندسية: الـ Evidence هو اللي يربط الكود + الناس + التغيير + الجودة + القيمة ببعضها.
OBJECTIVE 1 (تابع)

⏳ الهندسة تفكر في الزمان: Change · Quality · Evidence

1 · CHANGE PLAN

خطط لتغير الاحتياجات، الأخطاء (defects)، البيئات، وانتقال الملكية (ownership). أول بناء ليس نهائياً!

2 · QUALITY CHECK

الجودة تشمل Reliability (الاعتمادية) + Security (الأمان) + Usability (سهولة الاستخدام) + Maintainability (قابلية الصيانة). التوقعات لازم تطابق المخاطرة.

3 · EVIDENCE SHOW

الدليل يشمل Artefacts (مخرجات) + Reviews (مراجعات) + Tests (اختبارات) + Versions (إصدارات) + Limitations (حدود) — أشياء أي شخص ثاني يقدر يفحصها.

❌ "I think it works" ليس دليلاً — "أنا أعتقد أنه يشتغل" غير مقبول
OBJECTIVES 2 & 3

✅ جاهز أولاً، ثم حدد المشكلة (Readiness → Bounded Problem)

"Ready first. Then frame the problem." — لا تستعجل على تعريف المشكلة قبل ما تتأكد إنك جاهز.

1 · Prerequisite Readiness (الجاهزية المسبقة)

Approved case — تعرف بالضبط وش مسموح للمشروع يسويه.
Approved toolchain — تستخدم بس الأدوات المسموح بها لهذه الحالة.
Evidence rules — تعرف وش الدليل المطلوب تسجّله.
Readiness gap — تُسمّي وش الدعم اللي ناقصك بعد.

2 · Bounded Engineering Problem (المشكلة المحدودة)

User need — مين يحتاج وش؟
Stakeholder value — وش النتيجة المفيدة اللي يفترض البرنامج يخلقها؟
Credible success signal — وش الدليل القابل للقياس اللي يبرز التقدم؟
Boundary — وش اللي داخل بوضوح وخارج بوضوح من المشكلة؟
⚠️ فخ الاختبار: Ready ≠ Confident — الجاهزية ليست الثقة! الجاهزية تعني أن الـ approved case, tools, evidence rules واضحة ومحددة.

🛠️ تطبيق عملي (Hands-on MCQ)

حلها بنفسك الأول، ثم اضغط على السؤال عشان تشوف الإجابة والشرح:

▶ السؤال 1: ميزة الرفع (upload) تشتغل. أي مهمة تعتبر Software Engineering أساساً؟

A) أضف فحص لنوع الملف واختبره
B) خطط لكيفية التعامل مع المستخدمين والتحديثات والأخطاء
C) أعد هيكلة دالة الرفع وحدّث التعليقات

✅ الجواب: B

لأن التخطيط للمستخدمين والتحديثات والأخطاء = تفكير عبر الزمن والناس والتغيير — وهذا جوهر الهندسة. A و C مجرد مهام برمجة مباشرة (كود فقط).

▶ السؤال 2: الفريق يعرف Python. أي خيار يُظهر الجاهزية (Readiness) بشكل صحيح؟

A) Approved case, allowed tools, evidence rules, readiness gap
B) Approved case, familiar tools, coding rules, first feature
C) Project goal, allowed tools, team confidence, first feature

✅ الجواب: A

الجاهزية = العناصر الأربعة الرسمية. "Familiar tools" فخ — لازم allowed (مسموح) مو familiar (مألوف)! و B تنقصها evidence rules والـ gap. أما C فتخلط بين الجاهزية والثقة (Ready ≠ Confident).

▶ السؤال 3: صف 10 يسلّم ملف PDF واحد للمعرض. أي مشكلة "محدودة" (bounded) بشكل صحيح؟

A) رفع أسهل للمعرض؛ النجاح = أغلب الطلاب يفضّلونه
B) تحسين رفعات صف 10؛ النجاح = أسئلة دعم أقل
C) رفع ملف PDF واحد؛ النجاح = 90% من الرفعات الصحيحة تكتمل

✅ الجواب: C

لأن فيها نطاق واضح (ملف PDF واحد) + إشارة نجاح قابلة للقياس (90%). A تعتمد على التفضيل (مشاعر مو قياس)، و B أقل تحديداً.

⚖️ الصح vs الخطأ (Right vs Wrong)

✅ افعل هذا (Right)
  • ✔️افحص الزمن، الناس، التغيير، والمخاطرة (Time, People, Change, Risk).
  • ✔️شمّل Code, Data, People, Dependencies في تفكيرك.
  • ✔️سجّل Readiness gaps وEvidence بالورق.
  • ✔️اربط Stakeholder value بـ إشارة نجاح قابلة للقياس وحدود واضحة.
❌ لا تفعل هذا (Wrong)
  • ✖️تعامل الهندسة على إنها مجرد كود أكثر.
  • ✖️تنظر للـ كود فقط وتتجاهل باقي النظام.
  • ✖️تعتبر الثقة دليل على الإتقان (Confidence ≠ Proof).
  • ✖️تترك المشكلة واسعة وغير محددة.

🔥 حيل الاختبار (Exam Hacks)

إذا شفت: "users, updates, failures, over time" → الجواب: Software Engineering (مو مجرد برمجة)
إذا شفت: "code + data + interfaces + people + procedures + dependencies + operating conditions" → الجواب: System
إذا شفت: "evolving needs, defects, environments, ownership" → الجواب: Change (PLAN)
إذا شفت: "reliability, security, usability, maintainability" → الجواب: Quality (CHECK)
إذا شفت: "artefacts, reviews, tests, versions, limitations, inspected by another person" → الجواب: Evidence (SHOW)
إذا شفت: "approved case, approved toolchain, evidence rules, readiness gap" → الجواب: Prerequisite Readiness
إذا شفت: "user need, stakeholder value, credible success signal, boundary" → الجواب: Bounded Engineering Problem
إذا شفت: "confident", "familiar tools", "team confidence" → الجواب: خطأ! Ready ≠ Confident
